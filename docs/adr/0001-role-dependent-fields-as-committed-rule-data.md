# Role-dependent fields are committed format rules, applied before deduplication

Some fields of a record are disclosable to the data subject only when they hold a particular role on it. In an occurrence report, the reported time, summary and original incident report go to the data subject when they are the person reporting, and are third-party data otherwise. We encode this as a generic span-rule step in the extraction pipeline, with the occurrence-report wording ("Person reporting", the three field labels) committed as rule data, because deployments are built from this repository and a per-instance settings page does not exist yet. The rule runs on each detector's output **before** priority deduplication, because deduplication drops spans that sit inside a higher-priority span: removing a whole-field span afterwards would disclose any third-party name inside it that a lower-priority detector had found.

## Consequences

- **An exception to "no suggestion is silently discarded".** When the data subject is confirmed as the reporting person, the whole-field span is removed with no redaction row and no rationale. That rule exists to stop uncertain identity matches from hiding third-party data. Here the decision is a confident one, and every uncertain outcome (no role line, an ambiguous name, more than one record in the document) redacts the field instead.
- **Operational codes inside a disclosed field are only redacted if a detector finds them on their own.** Today nothing detects a closure code such as `SE1 AS14` separately, so in the reporting-person branch it is disclosed. Accepted for now and out of scope.
- **Organisation-specific wording sits in the public codebase.** The intended future is per-instance configurable rules, stored alongside the custom recognizers and edited on the Settings page, and per team once teams exist (see [ADR-0002](0002-teams-not-modelled-yet.md)). The rule data is kept declarative so that move relocates it, not rewrites it.
